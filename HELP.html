1. Introduction

Pegasus Android Detector is a Lazarus / Free Pascal desktop tool that scans an Android device (through ADB) or a folder of .apk files and flags apps that match known indicators of NSO Group Pegasus and other mercenary-spyware families.

Detection is indicator-driven: the program does not attempt to "guess" whether an app is malicious from behaviour. Instead it compares each app against two kinds of threat-intel definitions:

  • Family rule files (*.txt) — human-editable rules for package names, hashes, signers, permissions, strings, classes and network indicators.
  • STIX 2.1 indicator bundles (*.stix2) — the same IoC files indexed by the MVT project.

An app is reported as critical only when it matches one of these definitions. There are no generic permission, heuristic or behavioural checks — the tool is deliberately limited to Pegasus / mercenary-spyware IoC matching to keep false positives low and results interpretable.

Scope note: this tool matches published indicators. A clean result means no known indicator was found, not a guarantee that a device is free of spyware. Indicator databases are always incomplete for highly targeted threats such as Pegasus.

1.1 What it detects

The scanner currently performs exactly two detection passes per application:

  1. Family-rule matching (signature findings) — package-name wildcards, SHA-256 / SHA-1 / MD5 hashes, code-signing certificates (DN and SHA-256), native library (.so) names, asset paths, permissions, embedded strings, component (class) names, and domain / IP / URL / email indicators defined in *.txt rule files.
  2. STIX2 indicator matching (stix findings) — known C2 domains (including sub-domains), IPv4 / IPv6 addresses, URLs, email addresses, file hashes, file paths / names, package names, device properties, process names and signer-certificate hashes loaded from *.stix2 files.

Both passes operate on the same per-app material: the app's package name, the SHA-256 and MD5 of its APK, its code-signing certificate, the permissions and components declared in its manifest, and printable strings extracted from its DEX bytecode.

2. Detection data

All definitions live in the data/ directory (configurable via RulesDir). On startup the scanner loads every *.txt and *.stix2 file found there and logs how many were loaded.

2.1 Family rule files (*.txt)

These are optional, hand-maintained rules. One key: value pair per line; a family: line starts a new rule block, and every following key belongs to that block until the next family: line. Lines starting with # are comments and blank lines are ignored. 

# family: NSO-Pegasus
# name: Pegasus Android implant (verified package name)
# severity: critical
# package: com.example.pegasus

family: NSO-Pegasus
name: Pegasus Android implant
severity: critical
package: com.skynet.*
sha256: aabbcc...ff
string: pegasus-c2.example.com

Recognised keys and the IOC kind each maps to:

Hard vs. soft indicators. A hard indicator (package, sha256, md5, cert) matches a family on its own. A soft indicator (perm, string, class) must appear at least twice in the same rule block before the family is considered matched, to reduce false positives.

2.2 STIX 2.1 indicator files (*.stix2)

The parser reads the raw JSON bundle text (no external JSON library) and extracts every "pattern" value. The recognised pattern types are: 

[domain-name:value='example.com']
[ipv4-addr:value='1.2.3.4']
[ipv6-addr:value='::1']
[url:value='http://example.com/a']
[email-addr:value='x@example.com']
[file:hashes.'SHA-256' = '...']   (also 'SHA-1' and 'MD5')
[file:path='/data/local/tmp/dropbox']
[file:name='roleaccountd.plist']
[android-package-name:value='com.example.app']
[android-property:name='sys.brand.note']
[process:name='fservernetd']
[x509-certificate:hashes.'SHA-256' = '...']   (also 'SHA-1')

The family name is derived from the file name:

  • file name contains pegasus → NSO-Pegasus
  • file name contains android → MVT-Android-Campaign
  • otherwise → the lower-cased file name without its extension

Included by default:

FileFamilySource
data/pegasus.stix2NSO-PegasusAmnesty International — 2021-07-18_nso/pegasus.stix2
data/android_campaign.stix2MVT-Android-CampaignAmnesty International / Google — 2023-03-29_android_campaign/malware.stix2

2.3 Refreshing definitions

To update the indicators, replace the *.stix2 files in data/ with newer ones (keep the .stix2 suffix) and/or edit the *.txt rules. No recompilation is needed — files are re-read at the start of every scan.

3. Scan modes

The tool offers three scan entry points, all sharing the same detection engine:

ModeHow to startDescription
Device scan GUI “Scan Device” button, or pegasus_cli --device SERIAL Enumerates installed packages over ADB, pulls each APK and analyses it.
APK folder scan GUI “Scan APKs…” button, or pegasus_cli --demo DIR Scans every .apk in a local folder; no device required.
Single-package scan Internal API (ScanOne) Scans one named package on a connected device.

A device scan needs USB debugging enabled and authorised on the phone, plus an adb executable (bundled as bin\adb.exe). An APK folder scan is fully offline.

4. How a device scan works

A device scan runs the following pipeline. Each ADB command is listed next to its purpose.

StepActionADB command
1List connected devicesadb devices
2Read device modeladb -s SERIAL shell getprop ro.product.model
3Read Android versionadb -s SERIAL shell getprop ro.build.version.release
4List packages (third-party by default)adb -s SERIAL shell pm list packages -3 (or pm list packages with --all)
5Resolve the APK path for one packageadb -s SERIAL shell pm path PACKAGE
6Pull the APK to the working directoryadb -s SERIAL pull /data/app/.../base.apk local.apk
7Read signer + installer packageadb -s SERIAL shell dumpsys package PACKAGE

Steps 5–7 repeat for every package (bounded by MaxApkPull). For each pulled APK the program then:

  1. Verifies the file is a valid APK (ZIP PK magic bytes).
  2. Analyses the APK (hashing, manifest parsing, DEX string extraction) — see section 7.
  3. Runs the two IoC matching passes — see section 6.
  4. Records the app result and any findings.
Why pull the whole APK? hashes, the code-signing certificate, and DEX strings are only available from the actual APK bytes, so the scanner copies each package locally and analyses it there. Pulled files go to the configured working directory.
Caching. APKs already present in the working directory are reused instead of being downloaded again. When you scan a different device, the working directory is cleared automatically first. Use the Clear… button (GUI) or --clear (CLI) to wipe it manually.

4.1 Enabling USB debugging

  1. Open Settings → About phone and tap Build number seven times until “You are now a developer” appears (the exact location varies by vendor).
  2. Open Settings → System → Developer options (on some devices this is under Additional settings).
  3. Turn on USB debugging.
  4. Connect the phone to the computer with a USB cable and choose File transfer / MTP if prompted.
  5. On the phone, tap Allow on the “Allow USB debugging?” prompt (optionally tick “Always allow from this computer”).
  6. Run adb devices — the phone should be listed as device. If it shows unauthorized, re-check the prompt on the phone.
Some vendors hide the Developer options menu until OEM unlocking is enabled or until you sign in to the vendor account.

4.2 Getting root access

Root is only needed for the optional message scan: reading SMS requires mmssms.db under /data/data, which ADB cannot access on a normal device. The APK scan works without root.

Warning. Rooting can void your warranty, block OTA updates and reduce device security. Only root a device you own, and back it up first.
  • Pixel / Nexus: unlock the bootloader with fastboot flashing unlock and boot a Magisk-patched image.
  • Other brands: follow a device-specific guide (typically a patched boot image or a TWRP recovery); the steps differ per model.
  • Emulator alternative: an Android emulator or a dedicated test phone can provide adb root and full /data/data access without modifying a personal device.

After rooting, verify access with adb root or adb shell su -c id before enabling --messages.

5. How an APK folder scan works

The “Scan APKs…” button / --demo DIR path skips all ADB steps and operates directly on local files:

  1. Enumerate *.apk files in the selected folder.
  2. For each file, run the same analysis pipeline: hash, parse the manifest, extract DEX strings.
  3. Run the same two IoC matching passes and record findings.

Because no device is involved, fields such as device model and Android version are left empty and the report is labelled (demo). The signer and installer-package fields are also unavailable (they come from dumpsys package), so cert-based rules cannot match in this mode.

6. How matching works

Every app is scored against the loaded definitions. A match produces a finding (an individual observation) and adds the matched family to the app's family list.

6.1 Family-rule matching

Each *.txt rule block is evaluated against the app with the BlockMatches logic:

  • package — wildcard match against the app's package name (supports * and ?).
  • sha256 / md5 — case-insensitive exact match against the APK hashes.
  • cert — case-insensitive substring match against the code-signing certificate.
  • domain / ip / url / email — case-insensitive substring search across all extracted DEX strings.
  • perm — exact match against a declared manifest permission.
  • string — substring search across extracted DEX strings.
  • class — substring search across declared manifest components.

A block is considered a match if any hard indicator matches, or if two or more soft indicators (perm, string, class) match.

On a match, the block's severity and name are used to create a finding of kind signature, and the block's family is added to the app's matched-family list.

6.2 STIX2 matching

The STIX2 pass checks each app against every loaded *.stix2 bundle:

Domain matching is sub-domain aware: a string such as mail.pegasus.example.com will also match an indicator for pegasus.example.com and example.com by progressively stripping leading labels.

Device-level indicators. The device property, file path and process name indicators are checked against the live device via ADB, so they only apply to device scans — not offline APK-folder scans.

6.3 Scoring & severity

The app-level score is a coarse summary: an app is scored 100 / critical if it matched at least one family or STIX2 indicator, and 0 / none otherwise.

Severity values used throughout the tool:

ValueMeaning
noneno indicator matched
lowlow-confidence / low-impact indicator
mediumnotable indicator
highstrong indicator
criticalknown spyware package / hash / C2

Individual findings keep their own severity (for example, an email IOC finding is high, while a package or C2-domain finding is critical), which is what appears in the report's findings table.

7. How APK files are analysed

For each APK the scanner extracts the material the IoC rules need:

  1. Hashing — the whole APK file is hashed with SHA-256, SHA-1 and MD5. These are compared against sha256:/sha1:/md5: rules and STIX2 file-hash indicators.
  2. Manifest parsing — the APK is a ZIP archive; the binary AndroidManifest.xml (AXML) is unpacked and parsed to recover the package name, declared permissions, and components (activities, services, receivers, providers), plus whether the app declares a launcher activity.
  3. String extraction — if enabled, top-level classes*.dex files are scanned for printable ASCII strings of at least MinStringLen characters (default 6). The result is sorted and de-duplicated. This is the corpus searched for C2 domains, IPs, URLs, emails and string: rules.
  4. Archive enumeration — native library names (lib/**/*.so), asset paths and every file name are collected to enable lib:/asset: rules and STIX2 file:name matching.
  5. Certificate fingerprint — the signer certificate is extracted from the v1 signature block (META-INF/*.RSA|.DSA|.EC) and hashed with SHA-256/SHA-1 to match cert_sha256: rules and STIX2 x509-certificate indicators.

String extraction is controlled by ExtractStrings and MinStringLen in the configuration. Disabling it skips all string/domain/IP/URL/email matching (only package, hash, permission and class indicators remain effective).

After a scan the program writes three files into the report directory and (in the GUI) opens the HTML version in the browser:

.htmlStyled tables for applications and findings.
.jsonMachine-readable structure (see below).

8.1 JSON structure

{
  "device": "...",
  "model": "...",
  "android": "...",
  "started": "...", "finished": "...",
  "apps": [
    {
      "package": "com.example.app",
      "score": 100,
      "severity": "critical",
      "sha256": "...",
      "sha1": "...",
      "md5": "...",
      "cert_sha256": "...",
      "signer": "...",
      "installer": "...",
      "has_launcher": true,
      "families": ["NSO-Pegasus"]

  ],
  "findings": [
    { "app": "com.example.app", "kind": "stix", "severity": "critical", "detail": "..." }

families is the list of threat families the app matched; it is empty for clean apps. Each finding has a kind of signature (txt rule) or stix (STIX2 indicator), a severity, and a human-readable detail.

11. Building from source

The project requires Lazarus (LCL) and Free Pascal 3.2.2. Three batch files drive the build (adjust LAZ_ROOT if your install path differs):

ScriptOutput

Source layout:

  • src/scanner.pas — scan orchestration and IoC matching.
  • src/signatures.pas — *.txt rule loader and wildcard matching.
  • src/stix2.pas — dependency-free STIX 2.1 indicator parser.
  • src/apk.pas — APK hashing, unpacking and DEX string extraction.
  • src/manifest.pas — binary AXML manifest parser.
  • src/adb.pas — ADB process wrapper.
  • src/report.pas — HTML / JSON / text report generators.
  • src/config.pas — config.ini handling.
  • src/main.pas, src/consoleapp.pas — GUI and console front ends.

12. Limitations & privacy

  • Known-indicator matching only. The tool detects only what its definitions describe. It cannot identify unknown or zero-day spyware, and a clean report is not a security guarantee.
  • Indicator freshness. The bundled pegasus.stix2 and android_campaign.stix2 come from specific Amnesty International / Google investigations. Refresh them before operational use.
  • Device scan needs USB debugging. Enable Developer Options → USB debugging and authorise the computer on the device.
  • APK folder scan has no signer data. Because dumpsys package is a device command, cert: rules cannot match in offline/demo mode.
  • Split APKs. Only the primary base.apk path returned by pm path is pulled; additional split APKs are not fetched.
  • Privacy. A device scan copies APK files to the local working directory and generates local reports. It does not upload data anywhere. When message scanning is enabled, the scanned messages (bodies) are included in the report and matched ones are highlighted. Review reports before sharing.
